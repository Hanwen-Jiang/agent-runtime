# 面试笔记：怎么知道一次 Coding Agent 优化真的有用？

## 面试时可以这样讲（约 90 秒）

> 我们先用 5 道题跑通从 Issue 到补丁、再到官方判分的全过程，再固定 50 道 SWE-bench Verified 做版本回归。判断修复是否成功，看补丁能不能通过目标测试并保住原有测试。Agent 自己说“完成了”，只是排查时的一条线索。
>
> 有一次，基线里 3 道题各用了约 150 次工具调用，最后连一行代码都没改。我们翻了执行记录，发现值得改的是 Agent 什么时候从阅读转向动手。于是给有写权限的节点加了提醒：连续 20 次只读，就提示它回到修改目标。我们也改了 Reviewer，让它在结束任务前检查有没有实际改动、改完有没有验证。这里有个容易做错的决定：最后一次测试返回非零的 20 道题里，官方判分仍然解决了 12 道，所以我们把退出码交给 Reviewer 判断，没有把它写成硬性否决条件。
>
> 在这组调优中，基线解决 32 题，第一轮 34 题，第二轮又回到 31 题。这让我形成了一个习惯：既看新修好的题，也看原来能修、现在修不好的题，还要看每个结果花了多少钱。几项改动一起上线时，我会把结论表述为版本差异；要说某一项机制有效，还需要单独验证。

## 我们当时怎样做决策

| 环节 | 项目里发生了什么 | 得到的判断 |
| --- | --- | --- |
| 校验评测环境 | 把官方修复补丁送进判分器，发现一个旧版 requests 用例连官方补丁也失败，原因是外部服务的证书校验。正式样本记录了对该仓库的排除。 | 遇到失败，先分清补丁错误、环境错误和判分异常，三者的修复方向完全不同。 |
| 固定基线 | 从剩余题目里按仓库和难度分层，固定种子 0，后续版本用相同题号。GPT-5.5 基线为 32/50，费用约 27.11 美元。 | 重复用同一组题，才能找到哪些题的结果翻转；这组题适合调试，容易被反复调优影响。 |
| 用轨迹筛选假设 | 我们一度怀疑压缩导致重复读取。1,893 次读取里有 179 次完全重复，成功题与失败题的重复占比分别约 7% 和 8%。反倒是 3 道空补丁题都耗尽了约 150 次工具调用。 | 放下证据薄弱的压缩假设，优先处理只读不改、错误调用后无法纠正、没有验证就收尾等具体行为。 |
| 让失败可纠正 | 除只读提醒和 Reviewer 检查外，工具参数错误会附上纠正说明，最多重问两次。调优第一轮跑了 14 题，又发现 Reviewer 把可写任务描述成只读，Planner 使用了过期预算；该批次单列，修好后从头跑。 | 每轮要保留版本和运行条件。中途改过系统的两个半批次不能拼成一次对照。 |

| 比较 | 实际结果 | 能回答什么 |
| --- | --- | --- |

## 其他团队怎样优化

| 公开案例 | 他们怎样找问题、改设计、验证结果 | 我们可以借鉴什么 |
| --- | --- | --- |
| **Princeton 的 SWE-agent：优化工具接口** | 团队先在少量开发题上观察 Agent 的编辑和搜索行为，再比较不同工具设计。在同一模型和 SWE-bench Lite 上，提供编辑动作时解决率为 15%，编辑后再加 lint 检查为 18%。这组消融把问题缩小到了一个可切换的工具行为。[论文 §5.1、表 3](https://arxiv.org/html/2405.15793v3#S5.SS1) | 可以固定模型、题目和预算，只开关“连续只读提醒”。既数新增修好的题，也数误打断正常探索的题。这个验证仍待做。 |
| **Anthropic Research：优化开放式研究任务** | 从约 20 个代表用户用法的问题开始，看子 Agent 怎样分工、选择来源和引用证据。研究答案通常没有唯一字符串，团队用事实准确、引用准确、完整性等标准评分；人工试用还发现了模型偏好搜索排名较高、质量却较低的来源，促使团队调整选源指引。[团队复盘](https://www.anthropic.com/research/multi-agent-research-system) | 对代码补丁可以跑测试；对我们的文档问答，应抽查“引用是否真的支持结论”。检索命中、答案正确、证据可信要分开记。 |
| **Cursor Bugbot：把离线分数连到用户动作** | 离线用带人工缺陷标注的真实代码差异做 BugBench；线上看 PR 合并时，开发者是否修复了被指出的问题。他们还和 PR 作者抽查判断结果，同时跟踪每次审查发现的问题数，避免少报问题也让修复比例变好看。[团队复盘](https://cursor.com/blog/building-bugbot) | 对我们的 Issue 到 PR 工作台，可设计“产出可审阅补丁”和“经审阅后被接受”两项指标，各自注明分母。这是下一步产品评测设想，现有 SWE 分数衡量的是补丁通过测试。 |

## 别人测哪些题？我们的 38/50 放在哪里？

公开报告里的“小集”有不同用途。官方 [SWE-bench Lite](https://www.swebench.com/lite.html) 是从原始 SWE-bench 筛出的 300 道测试题，偏向单文件、改动较集中的修复，另有 23 道开发题。社区的 [Verified Mini 固定 50 题](https://github.com/mariushobbhahn/SWEBench-verified-mini/blob/1ce432065d9ed226017ef1ac88b5f91818383c64/data/subsets/size_optimized_sample_ids.json) 兼顾历史模型表现分布和镜像成本，选了 25 道 Django 和 25 道 Sphinx，与我们的清单仅重合 6 道。Anthropic 则专门挑人工预计超过 1 小时的 45 道难题，Sonnet 4.5 平均解决 20.4 道（45.3%）。我们的同档题只有 3 道。[Mini 选题方法](https://github.com/mariushobbhahn/SWEBench-verified-mini) · [Sonnet 4.5 系统卡 §9.3.2](https://www-cdn.anthropic.com/963373e433e489a87a10c823c52a0a013e9172dd.pdf#page=139)

更有用的参照是比较同一批题。我取 [SWE-bench 官方逐题归档的固定版本](https://github.com/SWE-bench/experiments/tree/40f164d5b8f1d249bf95a6df8b74b577fd8e519d/evaluation/verified) 中目录名以 `20260217_mini-v2.0.0_` 开头的全部 11 个配置。它们都用 mini-SWE-agent v2.0.0，标注每题一次。将各目录的 `per_instance_details.json` 按我们的 50 个实例 ID 筛选，统计 `resolved=true`。每份记录都覆盖这 50 题。

| 模型配置（选列 5 个） | 我们的 50 题 | 对方完整 Verified 500 题 |
| --- | ---: | ---: |
| GPT-5 mini | 31/50（62%） | 281/500（56.2%） |
| DeepSeek V3.2 high | 34/50（68%） | 350/500（70.0%） |
| GPT-5.2 high | 38/50（76%） | 364/500（72.8%） |
| Gemini 3 Flash high | 40/50（80%） | 379/500（75.8%） |
| Claude Opus 4.5 high | 42/50（84%） | 384/500（76.8%） |

**面试口径：** 同题上，11 个公开配置解了 31–42 题，中位数 39 题。我们最终解了 38 题，接近这批配置的中位数。公开提交每题一次，我们的最终报告包含补跑，而且这 50 题用于项目调优。可以比同题解了多少，不能据此声称整套系统等同于哪个模型，或估算我们在完整 500 题上的解决率。

## 三个容易被追问的地方

**“所以简历上的 8 题，到底是哪项改动带来的？”** 目前能确认 10 道新增成功和 2 道原成功题未再成功。要归因，先看这 12 道的旧、新轨迹和补丁，再固定模型、工具权限、预算、并发和重试，只回退一项候选改动，最后用未参与调试的同类题复验。前面的 32→34→31 是另一组实验。

**“你的个人贡献怎么核对？”** 可以讲会话刷新后恢复进度这个功能。先定义快照缺失时的验收行为，再实现按游标补齐历史，只为未结束任务续接事件流。面试时打开[回归用例](https://github.com/Hanwen-Jiang/coding-agent/commit/35c9289f0540814f2b863d8ff235fbf461308c7c)和[实现提交](https://github.com/Hanwen-Jiang/coding-agent/commit/715223e228776fdca25ec1514618e6dc47426023)，具体指出自己定了哪个边界、用了 AI 做哪一步、最后怎样验证。项目总分和个人交付各有证据。

**“有没有指标变好，你们还是保留旧方案的例子？”** 在 120 份合成文件和 100 条固定查询上，引入 RAG 重排后，Hit@8 从 79% 升到 95%，但 CPU 侧 P95 从 0.265 秒升到 6.36 秒，超过了 2 秒目标。最终保留按需重排。这里测的是检索命中与延迟，回答正确率还需要带答案和证据的独立题集。[RAG 实验记录](../plan/evidence/file-engines-benchmark/README.md)
