# 模型预算共享账本实现（2026-11-03）

对应人工验收 Q38–Q54、MODEL-BUDGET-02。实现位于 `libs/go-core/modelbudget`，由 Gateway 和 Task Service 共用现有 `RelationalStore`，不另设预算数据库、Worker 账本或计量服务。本切片交付持久账本；服务启动、策略解析、调用预留与 Task 准入接线由同一工作项的集成切片验收。

## 计量事实与存储

此前 Gateway 的 `MeterRecord` 仅输出 JSON 日志，不能支持两个入口共享原子预留。现在把每次调用的预留和实际费用存入现有业务库中的 `model_usage`，使这份调用记录成为两处检查共同读取的权威事实。原有日志继续用于诊断，不另计一份余额。

迁移 301 创建两个表和一个时间索引：

- `model_usage`：调用标识、原始预留时间、预留微美元、实际微美元、Task、Node、Model Profile、供应商和方法。实际金额为 `NULL` 表示尚未得到可结算的 usage；`0` 表示已确认零费用。这是调用本身的预留/结算状态，不另存余额、每日汇总或恢复状态。
- `model_budget_lock`：每个租户作用域一行固定锁键，串行化同租户的预留与结算；不保存额度、费用或生命周期。
- `model_usage_by_time`：按预留时间筛选当前 UTC 自然月。累计查询在数据库内聚合，不把整月记录传回服务。

租户隔离复用 `RelationalStore.Bind`：SQLite 每租户库文件，PostgreSQL 使用既有 RLS。应用 SQL 不声明、读取或改写 `tenant_id`。Gateway 和 Task Service 必须连接同一业务库；各自的进程内计数不能替代这里的检查。

## API 与边界

`New(relational.Provider) *Ledger` 使用调用方管理的业务库，启动时先应用 `Migrations()`。共享 `Provider` 只包含：

| 操作 | 行为 |
| --- | --- |
| `Reserve(ctx, ReservationRequest)` | 开始供应商调用前，在同一事务内锁住本租户、累计日/月已用与预留、核对两项额度、插入调用记录。允许本次预留恰好用满额度；已达到任一启用上限时，零金额请求也拒绝。失败不留预留记录。 |
| `Settle(ctx, Reservation, actualUSDMicros)` | 用实际费用替换预留金额，自动释放多出的部分。相同句柄、相同实际金额的重复结算成功；不同第二次金额返回 `Conflict/reservation_already_settled`。伪造或其他租户的句柄不能改账。 |
| `Check(ctx, tenantID, at, Limits)` | Task 准入读取同一份已用与预留；达到启用上限即拒绝。该操作不假装为整个 Task 预留费用，每次模型调用仍需 Gateway 再执行 `Reserve`。 |

额度用整数微美元，`Enabled:false` 表示该周期未设限制，`Enabled:true, USDMicros:0` 表示零额度。策略继承和平台硬上限由共同的策略解析器处理，不保存在账本中。日/月边界均为 UTC，按调用开始时归属原周期；结算发生在次日或次月不会把旧调用挪到新周期。句柄时间规范为 UTC 毫秒，与持久记录一致。

真实费用超过预估也必须记账，不能因为“超过预留”丢弃供应商已经产生的账单；后续请求依据实际总额拒绝。调用方仍必须提供合理的费用上界并处理供应商 usage，账本不重新估 token、不按价格选择模型。

预算不足统一返回不可重试的 `Denied/tenant_budget_exceeded`。底层存储错误按既有 Provider 错误传播，不伪装成预算不足。成功取得的 `Reservation` 只在事务提交后返回。

## 中断后的处理

进程退出或未取得最终 usage 时保留原始预留，重启后仍计入日/月额度。调用方不能仅因断线、超时或取消就按零结算；取得已发生费用后再调用 `Settle`，相同结算可安全重试。

没有自动到期退款、后台扫描或周期归零任务。极少数失去响应、无法自动确定实际账单的调用，由运维依据供应商账单和调用归属记录确认后，使用原始句柄结算。没有费用证据时保留预留。这一限制要在服务调用链验收中明确，不得把“账本接口已实现”写成所有取消/流式计量均已闭环。

## 复杂度决策

| 字段 | 持久调用记录及时间索引 | 单租户固定锁行 |
| --- | --- | --- |
| Failure | 仅靠日志或内存无法在重启后核对已用/预留，两个入口可看到不同余额。 | 多个 Gateway 副本同时读取旧总额，各自通过检查后共同超过预算。 |
| Evidence | 现有 `writeMeter` 只写 JSON，Q47/Q48 要求开始前原子预留，Q51 要求双入口同源。 | 人工验收明确要求并发原子预留；真实 PostgreSQL 默认事务不会让两个普通查询互斥。 |
| Minimum fix | 在既有业务库保存每次调用的一行预留/实际费用；直接聚合当前周期。 | 复用现有事务，通过一行 `UPDATE` 锁串行化同租户检查和写入。 |
| Benefit | 重启后保留费用、释放多余预留，审计归属完整，两个入口读同一事实。 | 同租户并发不能超额预留，其他租户各自使用独立锁。 |
| Performance cost | 每次预留一次当前月聚合及插入，每次结算一次读和更新；月查询随本月调用记录增长，暂不引入汇总表。 | 每次预留/结算增加两条事务内 SQL，锁只覆盖短数据库事务，不覆盖模型调用。 |
| Implementation cost | 共享 Go 包、一项迁移与两种数据库的行为测试；不新增依赖。 | 固定键表与事务内两个语句，不新增调度器或分布式锁服务。 |
| Operational cost | 每次尝试一行；沿用业务库备份及容量管理。未知费用由运维按调用记录确认。 | 每租户一行，无过期、续租、扫表或修复任务。 |
| New failure surface | 业务库不可用会阻止新预留；丢失供应商最终 usage 会保留未结算额度。 | 同租户高并发可能等待锁；数据库按现有超时/错误策略处理。 |
| Release slice | MODEL-BUDGET-02 的共享账本，实现完成后由 Gateway/Task 集成验收。 | 与同一账本切片交付，真实 PostgreSQL 并发测试覆盖。 |
| Decision | KEEP：实际计费与并发预留是已批准需求；进程内 fake 或日志不能满足。 | KEEP：仅进程内互斥不能跨副本；使用可移植锁行，避免引入另一套锁系统。 |
| Removal condition | 只有用量权威迁移到另一份已验收的共享持久账本后才可移除，不能先撤掉计量。 | 当既有事务接口提供等价的、经两种数据库验收的原子额度操作时可替换；当前不再增加机制。 |

按预留/结算事件更新账本，不因无关 UI 请求、价格变更或历史 Task 重放扫描远端供应商。当前交付不添加周期汇总、后台对账、第二套证明状态或跨系统哈希。

## 验证

- Windows Go 1.26.5：首次账本实现的 8 个测试全部通过。
- WSL Debian，Go 1.26.5，真实 PostgreSQL 17.10：`AR_POSTGRES_BIN=/usr/lib/postgresql/17/bin go test -count=1 -v ./libs/go-core/modelbudget` 全部通过，9 个顶层测试；无跳过。
- SQLite 与真实 PostgreSQL 跑同一套双 Provider 并发、重新连接后可见、退款、结算幂等、超出预估的实际费用、日/月切换、零额度及租户隔离检查。32 个并发请求在 10 单位额度下仅 10 个成功。
- PostgreSQL 使用非超级用户、无 BYPASSRLS 的在线角色，`AuditRLS` 确认两张表均被租户隔离覆盖。
- 单独覆盖 UTC+8 表示的跨月时间、字段归属持久化、伪造句柄、负金额、取消上下文及显式零费用。

本验证不替代 Gateway 真实供应商/流式取消的费用验收，也不声称已在 k3s 完成双入口部署验收；这些由接线切片继续验证。
