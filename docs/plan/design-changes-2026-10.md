## C1　VectorStore 默认改为 Milvus

### 决定

- 生产实现改为 Milvus。`VectorStore` 接口不变（`libs/py-core/.../providers/vector_store.py`），核心代码不用改。
- **稀疏向量仍由服务端算好再写入，不用 Milvus 原生的 BM25 Function。** 原生 BM25 要把正文明文交给向量库，与附录 I.7 冲突：正文按租户密钥加密，向量做保距变换（稠密向量正交变换、稀疏向量下标置换）。服务端算好的稀疏向量照样可以置换。
- 现有的 Qdrant 适配器保留为备选实现，直到 Milvus 实现通过全部一致性测试与越权测试，并在夜间任务里稳定运行一段时间，再决定删不删。
- 开发与单元测试仍用内存实现。

### 替换原文

**1.5 第一段**，把“Qdrant 量化加分片”改为“Milvus 集群（HNSW 索引，规模上来后改 DiskANN 或量化索引）”。

| 记忆向量规模 | Milvus 中的向量条数 | 3,000 万条 | 超过 5,000 万：开启量化索引并增加 Query Node；超过 1.5 亿：评估 DiskANN 或 GPU 索引 |

**2.4 接口一览**，VectorStore 一行的推荐实现由“Qdrant”改为“Milvus”。

**3.4.1 第一段**，“向量存于 Qdrant”改为“向量存于 Milvus”。

**4.4 VectorStore 整节**替换为（图 23 要按 Milvus 的集合布局重画）：

> **接口**：按租户写入与删除向量；稠密 + 稀疏混合查询并融合排序；按字段过滤；按 embedding_version 双写迁移。
>
> **推荐实现**：Milvus。每个（语料、embedding_version）一个集合，稠密向量与稀疏向量是同一集合里的两个向量字段；稀疏向量由 Memory Service 算好写入（BM25 或 SPLADE 类），不用 Milvus 原生的 BM25 Function，因为那要把明文交给向量库（附录 I.7）。租户字段设为 partition key，每次读写、查询、计数、删除都由适配器拼上租户条件，过滤值一律经表达式模板参数传入，不拼接字符串；平台级条目放在独立的只读集合。需要写后即读的路径用 Strong 一致性级别（Milvus 默认的 Bounded 可能读不到刚写入的数据）。
>
> **优势**：面向亿级向量设计，存算分离，Query Node 可以单独扩展；索引种类多（HNSW、IVF、DiskANN、GPU 索引），规模变化时换索引而不换组件；一次请求完成稠密与稀疏检索。
>
> **代价与对策**：组件多：单机版依赖 etcd 与对象存储，集群版组件更多，要用 Operator 或 Helm 部署；本地开发与集成测试需要 Linux 容器环境（Windows 上要 WSL2 + Docker），单元测试用内存实现。向量超过 5,000 万时开启量化索引并扩 Query Node，超过 1.5 亿时评估 DiskANN 或 GPU 索引；需要处理百万级长文档或代码库全文检索时，再引入 OpenSearch。

**附录 I.6“多租户布局”一段**改为：

> 多租户布局：默认每个集合按租户字段分区（Milvus 的 partition key），每次查询都由适配器带租户过滤；大租户或合规要求高的租户升级为独立集合，乃至独立 database、独立集群与独立密钥。Workspace、User 作为分区内的过滤字段；Platform 级经验放独立的只读集合。

### 风险：本机跑不了 Milvus

2026-10-24 核对：这台机器没有 Docker，也没有装 WSL。现有测试靠 PATH 上的 `qdrant` 单个可执行文件拉起临时实例，Milvus 没有 Windows 原生版本（Milvus Lite 只支持 Linux 与 macOS，以官方文档为准）。可选：

1. 在本机装 WSL2 + Docker（要管理员权限，由你来装）。
2. 在一台 Linux 主机上跑一个共用的 Milvus，测试经 `AR_MILVUS_URL` 连接，每次运行用随机前缀的集合并在结束时清理。
3. 本机只跑内存实现，Milvus 的测试只在 CI 与夜间任务里跑（GitHub Actions 的 Ubuntu 有 Docker）。

## C7　文档知识的分块、版本与入库

### 替换原文

**附录 I.6** 表格“Workspace 知识”一行改为：

| Workspace 知识：文档、工单、wiki | 叶子片段 + 上下文前缀（标题与小节路径；可选的模型说明） | 文档 ID、版本、小节路径、父块、源系统权限、更新时间 | 混合召回 + 重排 + 权威复核；权限继承源系统；按语料修订号固定版本 |

表后、“检索流水线”前加一小节：

> **Workspace 知识的分块、版本与入库**
>
> - **两层分块**：叶子片段是检索单位，按 token 计（默认约 300 到 500，小重叠），沿段落与句子边界切，表格与代码块不切断；父块是展开单位，取文档结构（标题层级下的小节、页、表格），超过上限再按 token 切。数值是检索预设的参数，由评测决定。
> - **上下文前缀**：叶子入索引的文本是“文档标题 + 小节路径 + 正文”；可以按租户预算再加一句由轻档模型生成的说明，记在后台任务的预算上。
> - **只返回叶子与父块地址**：检索不合并父子块。要不要把同一父块下命中两个以上的叶子换成父块，由 Context Builder 按预算决定；agent 也可以用只读工具按地址取父块。
> - **片段身份**：tenant、workspace、文档、版本、小节路径、层级、父块、内容哈希、embedding_version、源系统权限、sensitivity。片段 id 按内容寻址，新版本里没变的片段复用旧向量。
> - **版本与发布**：新版本完整构建并核对清单后才发布；构建失败不影响当前版本。每个 Workspace 的知识库有一个单调递增的语料修订号，每次发布加一；片段带生效区间 [published_rev, retired_rev)。Task 开始时固定修订号 R（附录 B.1 的 pinned.data），检索条件为 published_rev ≤ R < retired_rev。旧版本等到没有运行中的 Task 固定它时再回收。
> - **入库流程**：offline 队列上的工作流（附录 K.5）：解析（program 节点，在 Sandbox 中执行，上传的文件不可信）→ 分块 → 可选的上下文说明 → 经 Model Gateway 嵌入 → 按片段 id 幂等写入 VectorStore 与 RelationalStore（大正文放 ObjectStore）→ 核对清单 → 在一个事务里推进语料修订号。解析器是可替换的插槽，开发实现只处理 Markdown 与纯文本。
> - **检索预设**：同一条流水线，三组参数。memory-default：带信任与新鲜度衰减；knowledge-default：不按新鲜度衰减，按来源优先级排序，重排之后做权威复核（权限、版本、删除），返回可引用的地址；code：grep 与符号优先，不用向量。
> - **失败与无结果分开**：检索后端出错报 transient；后端正常而没有命中时，返回“证据不足”，不返回空结果冒充。

### 影响

- Memory Service 的 proto 增加文档的提交、发布、按地址读取与语料修订号查询，片段的 schema 进 `/schemas`，走 S-01。
- 入库工作流改变 Memory Service 的部署：要有消费 offline 队列的 Worker。
