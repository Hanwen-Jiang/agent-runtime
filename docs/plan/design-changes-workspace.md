## W1　Sandbox 的后端

### 替换原文

4.10 的“**本期**”一段替换为：

> **接口**：创建环境（资源上限、网络策略、绑定的 workspace）、执行代码、读写文件、销毁。环境只属于创建它的作用域，别的作用域访问是 not_found；空闲超时自动回收。
>
> **实现**：开发用本地子进程（不隔离，只给开发与测试）。生产有两类后端，按租户策略的 `sandbox.backend` 选（W4），模型与请求都不能指定：
>
> - **Kubernetes Pod**：每个环境一个一次性 Pod，建在专用命名空间（Pod Security restricted、默认拒绝进出的网络策略、没有 ServiceAccount 令牌、非 root、只读根文件系统）。隔离强度由 RuntimeClass 决定：gVisor（容器级，不需要 KVM）或 Kata（microVM，需要 KVM）。Pod 里的 agent 经 HTTP 接受执行与读写文件的请求，令牌由部署的密钥对环境 id 派生；Worker 只有在该命名空间里管理 Pod 的权限。
> - **Cloudflare Containers**：每个环境一个 Firecracker microVM，经 Cloudflare Worker 写的桥调用；出网可以全断或按域名放行。磁盘是临时的。
>
> 按域名放行的网络（`network = allowlist`）只有 microVM 后端支持；Kubernetes 的网络策略只能按 IP 放行，K8s 后端收到这类请求返回 invalid。

L.11 的表格后加一句：

> 本期实现了“容器 + gVisor”“microVM”两类（K8s 的 Kata、Cloudflare Containers），WASM 暂不做。Kata 用 Cloud Hypervisor，跑在 Kata 4 默认的 Rust 运行时上（工作区经 virtio-fs 挂进 VM）。

**E2B**（2026-10-27 用户定）：main 不接 E2B，只在这里提一句。自托管的 E2B（开源运行时 e2b-dev/runtime，跑在专用的 KVM 节点上，长于“带内存暂停与恢复”和 fork）放在单独的可插拔分支 `e2b`，设计、适配器与部署脚手架都在那里。

## W2　Workspace 层

### 为什么

现在的工作区是 Worker、应用与沙箱共用的一块本地盘（`<根>/<租户>/<workspace>`）。单节点能用，但多节点、Cloudflare 后端（磁盘是临时的、不在集群里）都不成立；应用直接读写这块盘，也绕过了 Runtime 的租户隔离与审计。

### 决定（建议）

1. 工作区是 Runtime 的一等对象，属于（租户，workspace id），生命周期跨 Task；应用不再直接碰它的文件。
2. 工作区由某个沙箱后端**承载**：活跃时在一个沙箱环境里（该环境挂着工作区的文件系统），空闲时**存档**到 ObjectStore，用时**恢复**。
3. 工作区内的工具（`repo_read`、`repo_list`、`repo_grep`、`repo_edit`、`shell_run`）都在承载它的沙箱里执行，不在 Worker 的文件系统上。
4. 应用经 **Workspace API** 管理工作区：建（从仓库地址克隆，凭据由应用传入、用完即弃）、看 diff、提交、推送、删除。推送是 write_irreversible，要有通过的 gate。
5. 同一个工作区同一时间只有一个写者：会写的 Task 持有工作区的租约，只读 Task 在快照上执行。

### 替换原文

4.10 之后新增一节：

> #### 4.10.1 Workspace
>
> **职责**：承载 Task 要读写的文件（代码仓库的工作副本、上传的数据），生命周期跨 Task；把文件放在沙箱里，让工具在隔离环境中读写与执行。
>
> **身份与作用域**：工作区属于（tenant_id, workspace_id），workspace_id 取自租户上下文（附录 A），别的作用域访问是 not_found。
>
> **生命周期**：
>
> 1. 创建：应用经 Workspace API 发起，可以从仓库地址克隆。克隆用的凭据由应用随请求传入，只在这次克隆里使用，Runtime 不保存。
> 2. 承载：用到时在租户策略选定的沙箱后端里起一个环境挂上工作区；环境空闲超时后存档并销毁。
> 3. 存档：打包成按内容寻址的分块，连同逐文件的清单（路径、权限、sha256）写入 ObjectStore；恢复时按清单核对，不一致按 transient 处理并重试恢复，仍不一致就报 invalid、不在半个工作区上执行。
> 4. 删除：工作区与它的存档一并删除；租户删除时一并删除（设计书现在没有租户删除的流程，这里先写明工作区一侧要做的）。
>
> **写者**：会写的 Task 开始时取得工作区的租约（带到期时间，随心跳续期），结束或失败时释放；租约在业务库里，以工作区为键唯一。只读 Task 在最近一次存档的快照上执行，看不到正在写的内容。
>
> **工具**：工作区内的读写与命令都经 Sandbox 接口在承载它的环境里执行；工具的 effect 不变（读是 read，改文件与执行命令是 write_reversible，作用范围限于工作区）。
>
> **Workspace API**（Task API 之外的一组接口，同样经 Ingress 认证）：创建、列出、取 diff（相对创建时或上次提交的版本）、提交、推送、存档、删除。推送是 write_irreversible：要有通过的 gate 记录，凭据由应用随请求传入，用完即弃；推送的目标分支由租户策略限定（例如只能推到 `agent/*`）。
>
> **计量**：每个工作区的沙箱存活时间、CPU 时间与存档大小记入 trace，计入租户的花费。

## W5　会话级沙箱

### 为什么

现在每条命令起一个一次性环境、跑完就销毁：microVM 每次多一两秒启动，工作区以外装的东西（系统包、全局缓存、跑着的服务）每条命令都没了，“先起数据库再跑测试”这类多步操作做不了。

### 决定（建议）

1. 环境按（租户，workspace，Session）复用：同一会话里第一次要用时创建，之后的命令都在它里面跑，空闲超过 idle_timeout（默认 15 分钟，租户策略可以调低）或活满 max_lifetime（默认 6 小时）才销毁；Session 关闭时立即销毁。
2. 命令之间只保证工作区里的内容（W2）。进程、`/tmp`、环境变量在环境活着时会留下，但不承诺：环境随时可能被回收，回收后下一条命令在新环境里跑。
3. 会写的 Task 持有工作区的租约（W2），所以一个工作区同一时间只有一个可写的环境；只读 Task 用另一个环境、在快照上跑。
4. 环境由哪个 Worker 副本用都一样：按（租户，workspace，Session）在环境表（W9）里查，不靠进程内的缓存；连 agent 的令牌由部署共用的密钥派生（已经这样做了）。
5. 联网授权（W8）属于 Task，不属于环境：Task 结束时收回，环境还活着也一样。

### 替换原文

4.10 的“实现”之后加：

> **环境的生命周期**：环境按（租户、workspace、Session）复用，空闲超过 idle_timeout 或活满 max_lifetime 时回收，Session 关闭时销毁。命令之间只保证工作区里的内容；进程与临时文件不承诺保留。会写的 Task 持有工作区的租约，一个工作区同一时间只有一个可写的环境。环境记在环境表里（见“环境表”），任何 Worker 副本都能找到并使用它。

### 影响

- Worker 的 `shell_run` 与 W2 之后的 `repo_*` 改为“查环境表、没有就建”，不再每条命令建与删。
- `SandboxSpec` 加 `session_id`（Python 接口，不是 proto）；空闲回收已有（K8s 适配器的注解与回收），改为以环境表为准。
- 一致性测试加：同一会话的两条命令看到同一个环境；空闲到期后换了新环境，工作区的内容还在。

### 待定的问题

1. Session 关闭的信号从哪来：Session 工作流空闲到期时发一个销毁事件，还是只靠 idle_timeout？建议两者都有，idle_timeout 兜底。

## W6　运行环境：多语言镜像与按项目定制

### 决定（建议）

1. **基础镜像**：部署登记若干“运行环境”，`SandboxSpec.runtime` 取其中一个名字。默认的 `universal` 装好常用工具链（Python 3.13、Node 22 LTS、Go、JDK 21、Rust stable、build-essential、git），另有几个只含单一语言的精简镜像。所有后端用同一份 Dockerfile 构建的同一个镜像（K8s 直接用，Cloudflare 按它构建），所以“换后端”不涉及迁移语言环境。
2. **固定与记录**：运行环境按镜像的 digest 固定，每次运行把 digest 记进 trace，复现时知道用的是哪个镜像。节点预先拉好基础镜像。
3. **按项目定制**（第二步）：仓库里有 `devcontainer.json`、`.tool-versions` 或 `Dockerfile` 时，第一次用到就构建一个镜像，键是“定义文件的哈希 + 基础镜像的 digest”，推到租户自己的镜像仓库路径下，之后直接用。构建在 microVM 沙箱里做（Dockerfile 来自用户，不可信），网络只能经包镜像（W7）与出网网关（W8）；有大小上限（例如 8 GB）、构建超时与每个租户的个数配额，长期不用的镜像定期清掉。

### 替换原文

4.10 的“实现”之后加：

> **运行环境**：沙箱的工具链来自镜像。部署登记若干运行环境（默认 `universal`，含常用语言的工具链），按 digest 固定，每次运行记下 digest；各后端用同一个镜像。仓库自带环境定义（devcontainer、.tool-versions、Dockerfile）时，在 microVM 沙箱里构建一次、按定义的哈希缓存复用，有大小、时间与个数上限。

### 影响

- `deploy/images` 加 `universal` 镜像（预计 3～4 GB）；沙箱后端登记把 runtime 映射到镜像（K8s 适配器已经支持）。
- 构建器是新组件（第二步），要在设计书 4.15 的仓库结构里登记。

### 待定的问题

1. 一个大的 `universal`，还是每种语言一个镜像？建议默认 `universal`（省得猜项目用什么语言），另给几个精简的给明确只用一种语言的租户。

## W7　包镜像

### 决定（建议）

做成按需拉取的缓存，不做全量镜像。沙箱只能连到它（默认断网时唯一能连的地方），它是集群里唯一能访问各家官方源的组件。

### 新增原文（4.10.2 包镜像）

> #### 4.10.2 包镜像
>
> **职责**：给沙箱装依赖用的本地镜像源，按需从官方源拉取并缓存；沙箱默认断网，装依赖只经它。
>
> **接口**：每种生态一个只读的路径，协议与官方源相同：PyPI（simple 索引）、npm（registry）、Go（GOPROXY 协议，另代理校验数据库）；Maven 与 crates 第二步再做。沙箱启动时注入 `PIP_INDEX_URL`、`npm_config_registry`、`GOPROXY` 等，项目不用改。
>
> **数据**：分两类。包文件（wheel、tarball、zip、jar）发布后不变，按 sha256 内容寻址、同一个文件只存一份，下载时核对上游给的哈希，不过期、只会被淘汰。元数据（索引页、npm 的包信息、版本列表）会变，单独的小预算，5 到 30 分钟过期，过期后先给旧的并在后台刷新，上游不可用时继续给旧的。元数据里的下载地址改写成指向镜像；npm 只取精简的包信息。同一个文件的并发请求只向上游拉一次。
>
> **容量**：包文件与元数据各有总预算（单节点起步 100 GB 与 5 GB）。用量到高水位（90%）开始淘汰，降到低水位（75%）停。淘汰用两段 LRU：第一次拉到的进试用段，再次被用才升到保护段，先淘汰试用段，一次性拉一大棵依赖树挤不掉常用的包。超过大小上限（默认 500 MB）的文件只转发、不落盘。常用包（基础镜像与常见锁文件里的）预热并常驻。下载到一半的临时文件与无主文件定期清掉。可选的第二层：本地淘汰的文件降到 ObjectStore（R2），未命中时先查它再去上游。
>
> **按租户的限制**：存储不按租户切（同一个包大家共用、只存一份）；按租户按天计“未命中时从上游拉的字节数”，超了之后只转发不缓存，再超就拒绝。命中不限。沙箱以环境的短期凭据访问镜像（凭据由部署的密钥对环境 id 派生，镜像据此在环境表里查到租户），所以远端后端也能经公网入口使用。
>
> **安全**：上游只有写死的官方源；租户的私有源不进共享缓存（第一期不支持私有源）。某个版本被曝恶意时，按“包名 + 版本”清除并拉黑，立即对所有租户生效。命中率、上游流量、淘汰量与各租户的未命中流量进 Telemetry。

### 影响

- 新服务 `services/go-pkg-mirror`（Go，只用标准库）；设计书 4.15 的仓库结构里登记。
- 部署：一块专用的卷；网络策略只放行沙箱到它、它到官方源；Grafana 面板加命中率与容量。
- 租户策略的配额（W10）里加“镜像未命中的字节数”。

### 待定的问题

1. 默认预算多大：单节点建议包文件 100 GB、元数据 5 GB，看命中率再调。
2. R2 冷层第一期就做，还是等加节点？建议等加节点。

## W8　出网网关与联网授权

### 决定（建议）

沙箱默认断网。需要联网的任务申请授权，人批准后经集群里的出网网关出去，到期自动收回；网关按授权放行，并按域名、端口、流量、时长限制，记下每个连接。

### 新增原文（4.10.3 出网与进网）

> #### 4.10.3 出网与进网
>
> **默认**：沙箱只能连包镜像（4.10.2）；别的出网一律断开。
>
> **联网授权**：授权属于一个 Task，内容是目标主机（可以用 `*.` 开头）、端口（默认 80、443）、到期时间与用量上限（上行、下行字节数，并发连接数，每秒请求数）。来源两种：提交 Task 时声明（Task API 的 `network_request`：主机与理由），或任务运行中由 agent 调 `request_network` 工具申请。两种都经 HumanChannel 问人，选项是“允许 15、30、60 分钟”与“拒绝”；由谁批（提交者本人、管理员、多人）按租户策略。租户策略另定上限：能放行的主机范围、授权的最长时长、每天的出网字节数、是否允许联网。批准的授权就是 gate 记录（附录 D.4），在它的范围与时限内的调用不再逐次审批；Task 结束或到期即收回。
>
> **出网网关**：沙箱经它出网（HTTP 代理，`HTTPS_PROXY` 带环境的短期凭据），网关按凭据在环境表里查到环境、Task 与授权。放行规则：HTTPS 看 SNI、HTTP 看 Host，必须在授权的主机里；端口在授权里；域名由网关自己解析并锁定地址，私有网段、链路本地地址（含云元数据地址 169.254.169.254）、集群内的服务与 Runtime 自己的端口一律拒绝；用量超了断开。每个连接记下租户、Task、目标主机、字节数与时长，进 trace。默认不解密 HTTPS；解密（限制方法与路径、检查请求体）只给明确要求防泄漏的租户另开。
>
> **进网**：沙箱不接受来自外网的连接。需要回调时（OAuth 跳回、Webhook），给环境的某个端口开一个预览地址（`https://<环境>.preview.<域名>`，经入口转发，带签名的短期令牌，有频率限制），同样要申请批准，随授权收回。
>
> **测试用的密钥**：用户把密钥存进本租户的 SecretStore，Runtime 在创建环境时以环境变量注入；日志与 trace 里只有名字与掩码，环境销毁即失效。
>
> **托管的 microVM 后端**（Cloudflare 等）没有我们的网关：授权的主机名单交给它们原生的出网白名单，字节数上限与逐连接的审计做不到；需要这两样的 Task 只落在集群里的后端。

附录 D.4 加一行：

> | 联网授权 | 由批准的授权覆盖 | 授权内可以 | 授权本身是 gate 记录；只读 Task 不能申请；到期、Task 结束即收回 |

### 影响

- 新服务 `services/go-egress-gateway`（Go，只用标准库；思路参考 Stripe 开源的 Smokescreen）；设计书 4.15 登记。
- 契约（S-01）：`SubmitTaskRequest.network_request`；租户策略的 `sandbox.network`（是否允许、主机范围、最长时长、每天字节数、谁来批）。
- Worker：`request_network` 工具（write_irreversible 级别，要审批）；创建环境时注入代理变量与测试用密钥。
- 部署：网络策略只放行沙箱到网关与包镜像；网关到外网；预览地址的入口路由。
- 有了网关，gVisor 沙箱也能按域名放行（计划第 4.2 节原来写的“完全访问只能落在 microVM”可以放宽为“按租户策略”，仍建议陌生租户用 microVM）。

### 待定的问题

1. 只读 Task 能不能申请联网？建议不能：联网的副作用按不可逆写处理。
2. 解密 HTTPS 要不要进第一期？建议不进。

## W9　沙箱环境表与对账

### 决定（建议）

Runtime 自己记下每个环境，所有后端的创建与销毁都经过环境表；定期与各后端实际在跑的对账，清掉孤儿；用量与花费从环境表出。现在各后端各管各的回收，没有全局视图。

### 替换原文

4.10 的“实现”之后加：

> **环境表**：每个环境在业务库里有一行（环境 id、后端、租户、workspace、Session、隔离强度、运行环境的 digest、创建时间、最近使用、到期、状态、CPU 时间、存活时间、花费），按租户行级安全。创建先记“创建中”再调后端，成功后记“就绪”；销毁先记“销毁中”再调后端。对账任务（Temporal 的定时工作流）定期列出各后端实际在跑的环境：环境表里没有或已销毁的，销毁；环境表里就绪而后端没有的，记为丢失。花费按后端的价目（部署登记）从存活时间与 CPU 时间算出，计入 Task 与租户的用量。联网授权（4.10.3）也记在这里。租户删除时销毁它的全部环境、收回全部授权（设计书现在没有租户删除的流程，这里先写明沙箱一侧要做的）。

### 影响

- 业务库加两张表（环境、联网授权）；RelationalStore 的迁移。
- 各后端要能列出在跑的环境：K8s 按标签列（已有）；Cloudflare 桥加一个列表接口。
- 对账是一个新的定时工作流（task-service 或 Worker 里跑，待定）；不在 Task Loop 核心链路上。

### 待定的问题

1. 对账工作流放 task-service（Go）还是 Worker（Python）？建议 Worker：各后端的适配器在 Python 侧。

## W10　跨后端的配额与预算

### 决定（建议）

配额与预算按环境表算，跨所有后端；现在每个后端各数各的（`max_envs_per_scope`）留作后端自己的安全上限。

### 替换原文

3.1.2 “职责”一段的括号改为：

> （Hook 声明、模型白名单、预算、沙箱后端与沙箱配额）

4.10 的“环境表”之后加：

> **配额与预算**：租户策略的 `sandbox.quota` 规定同时在跑的环境数、每天的沙箱时长（秒）、每天的出网字节数、每天的包镜像未命中字节数与每天、每月的沙箱花费。创建环境时在同一个事务里按环境表核对，超了拒绝（denied：`sandbox_quota_exceeded` 或 `sandbox_budget_exceeded`），不排队、不悄悄降级。沙箱花费与模型花费一起计入 Task 的预算。部署另有每个后端的容量上限（命名空间配额、托管后端的实例上限），两者取更严的。

### 影响

- 租户策略的 schema 加 `sandbox.quota`（S-01）。

## W11　有序回退

### 决定（建议）

后端暂时不可用（容量满、服务故障，即 transient）时按租户策略的回退列表换下一个；只能平级或升级隔离强度，绝不降级；denied 与 invalid 不回退。

### 替换原文

W4 那句之后加：

> 租户策略可以给回退列表 `sandbox.fallback`。所选后端在创建环境时报 transient（容量满、故障）时依次试下一个；隔离强度按 none < container < microvm 排序，回退的后端不能比 `sandbox.min_isolation`（没写时取第一个后端的强度）更弱；denied、invalid 不回退。Task 带联网授权且要字节上限与审计时，只在支持出网网关的后端之间回退。环境实际落在哪个后端、为什么回退，记进 trace 与环境表。工作区跨后端的回退要等工作区能存档与恢复（4.10.1）；在那之前只在共用同一工作区卷的后端之间回退（例如同一集群的 gvisor 与 kata）。

### 影响

- 租户策略的 schema 加 `sandbox.fallback`、`sandbox.min_isolation`（S-01）；保留 `sandbox.backend` 作首选。
- Worker 的后端选择改为“首选 + 回退”，测试覆盖：transient 时回退、denied 不回退、绝不降级、落点记进 trace。
