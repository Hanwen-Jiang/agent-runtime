## 设计

把同一个冻结的 Runtime C 分别跑在原 init-50 和公开 Mini 50 上。C 从上轮 Mini 50 的 B 派生，只改代码修复执行器的指令。节点同时具备编辑和 shell 工具时，让模型根据用户可观察的行为构造最小检查，尝试在原代码上确认失败，改完重跑同一检查，并验证一个相邻的正常行为。模型可以报告具体执行障碍。C 的工作树为 `e3646dd0ae3995fb8337eefad5dffa5a43417032`。[实际变更](candidate.patch) · [冻结记录](freeze.json)

| 题单 | 历史参照 | 如何检验候选 |
|---|---|---|
| init-50 | `t18-rev19` 解决 38/50，有 48 题获得明确判定。10 个明确失败中，7 个只失败在目标测试，2 个只失败在回归，1 个两类均失败。 | 固定原来的 11 个仓库、50 个题号；分别核对目标修复和回归。历史运行使用不同模型配置和总预算，分数变化按整个配置比较。 |
| Mini 50 | 原候选 B 解决 36/50，50 题均获官方判定。14 个未解题都有未通过的目标测试，回归测试全部通过。 | 固定原来的 25 个 Django、25 个 Sphinx 题及 GPT-6.2-sol，在每个已见与未见改善的题上比较。原 B 包含额度和环境恢复。 |

每一组都使用 `a6api/gpt-6.2-sol@2026-11`、`strong@medium` 和原官方评分器。两组各有 50 次题目执行机会，单题上限 $3、60 分钟、关闭 hints，共 6 个重叠题号，在各自的独立运行中重新生成。不能把两个分数池化成 100 个独立问题。候选没有题号特判。故障恢复沿用各自原运行的题号、工作区和记录，已经获得正式判定的补丁保留其判定。[基线逐题证据](baselines.json)

## 判读

主指标为官方解决数除以该组固定的 50 题。另记录官方判分覆盖、两版均通过、仅新版通过、仅旧版通过、两版均未通过和缺判的题。对新增或丢失的题核对目标测试和既有测试的汇总，检查模型花费和运行时长。环境故障、评分器异常、供应商余额和有效空补丁分别说明。只有全套完成后再判读结果。

选择候选的依据为两份题单的配对结果。若两组解决率均不下降、至少一组上升，再结合模型成本和具体退步例决定是否继续扩大验证。若出现一升一降，保留分组结果和失败例。两套都是开发者已观察过的题，单次差异只作为后续验证依据。
