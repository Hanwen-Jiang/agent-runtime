## 当场修复与实测

检查真实的 `VerificationRecord` 时，发现它会把超时或实际未运行任何用例的 Python 测试命令，记成“改动后已做验证”。这些空记录还可能覆盖上一个有意义的退出码。这个缺陷在本次探针中可复现；历史 SWE 归档不足以证明它就是上述 10 道未解题的原因。

做了一项改动：超时或可确认未收集用例的命令不计为有效验证，也不改写上一次有效退出码。普通非零测试结果仍交给 Reviewer 判断；例如项目本来就有失败的测试，不能据此断言修复未完成。文档改动和其他自定义业务检查保持原语义。当前空测试识别针对直接调用的 pytest / unittest 及 Python 的 `-m` 形式。

**实测结果：6/12 → 12/12。** 用 8 个真实的本机测试或检查进程产生观察值，将完全相同的观察依次送入修前、修后的记录器，再交给生产 Reviewer 决策逻辑。输入的模型完成建议固定，从而只测证据规则。4 个伪完成从 `done` 变为 `continue`；2 个先有有效检查、后有空检查的场景保留了正确的退出码；原先正确的 6 个对照全部保住。失败的真实测试允许记录为已运行，是为了保留 Reviewer 能判断既有失败的语义，不等于产品通过验收。

结果见[同输入前后对照](verification-results.json)。另以 CI 固定的 Temporal CLI 1.9.1 启动本地开发服务，Reviewer 和 ToolLoop 两组测试全部通过（45/45）；SWE 适配器的克隆重试、官方判分调用和难度拆分测试也通过（3/3）。验收集是专门为此缺陷写的机制回归，不是盲测或端到端 SWE 成绩。下一次模型回归应冻结模型、预算和重试设置，在未参与调优的任务上比较首次假完成、实际目标/回归测试结果及新增或退步的题号。不能把历史官方隐藏测试作为模型输入。

### 第二轮：收集到了用例，但一个也没执行

第一轮的 12 个场景通过后，新增三个独立检查：对实际存在的用例执行 `pytest --collect-only`、短选项 `--co`，以及一次真实用例失败后仅收集用例。pytest 在正常收集时可以返回 0，但不会执行断言。第一轮候选在扩展集上只通过 **12/15**，三项全部失败。随后仅改一处：识别 pytest 直接调用或 `python -m pytest` 的显式收集模式，忽略这次观察，保留上一次真正验证的退出码。选项终止符 `--` 后的同名路径不按选项处理。

复测同一组 15 个场景，原始版本 **6/15**，第二轮候选 **15/15**。另跑 Reviewer / ToolLoop（含本地 Temporal 开发服务）共 **47/47** 通过。这是固定 Reviewer 完成提案下的机制回归，与端到端 SWE 解决率分开报告。[改前逐项结果](verification-round2-before.json) · [改后逐项结果](verification-round2-final.json)
