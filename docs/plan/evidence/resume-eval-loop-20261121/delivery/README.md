# 会话断线与 Issue 交付验收（2026-11-21）

**在 Chrome 里同时注入 SSE 游标过期和会话快照不可用。** 让网页先打开一个会话，其中一个任务已经完成，另一个还在执行，最近事件 ID 为 5。随后服务端推送 `resnapshot_required`，快照接口再次返回 404，批量历史接口仍然可用。

| 浏览器观测，同一故障重复 5 次 | 原版 `0cd2c89` | 修复后 |
| --- | ---: | ---: |
| 整次恢复符合验收条件 | 0/5 | 5/5 |
| 对已完成任务重新打开事件流，每次 | 1 | 0 |
| 进行中任务的重连起点 | 无游标，从头重放 | 从已记录的事件 5 续传 |
| 会话批量历史请求，每次，含初次进入 | 1 | 2 |

初次打开页面原本就支持批量恢复。缺陷发生在**已经建立的连接过期之后**：页面绕过可用的批量 API，对每个任务重新打开事件流。改动集中在 `internal/web/static/app.js` 的 `resnapshot`：复用已有分页恢复函数，只对批量接口无法覆盖的任务逐个回放，并在异步返回后核对是否仍是原会话。用例要求页面重新显示结果、两次快照请求确实发生，以及新的活动流携带正确游标。在一已完成、一活动任务的夹具中，总请求数未减少；观察到的改善是取消了冗余事件流并避免从头读取活动历史，没有据此估算生产延迟。

**修后九个场景各跑五次，45/45 通过。** 覆盖正常评论交付、重复 webhook、领取后租约过期、发布中断、外部写入已发生但回执丢失，以及四种浏览器历史/恢复情形。回执丢失用例让工作区替身先记录一次外部推送再返回超时，重复轮询后精确核对 1 个任务、1 次外部写入、0 个 PR 和明确的失败状态，避免把结果未知写成发布成功。

环境为真实本地 Chrome、Go 服务逻辑和临时 PostgreSQL。GitHub、远端工作区及 Task API 使用测试替身。九个场景独立重复，不是同一条跨所有故障的线上请求，也没有发布真实 PR。
